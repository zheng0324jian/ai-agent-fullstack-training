# 作业一实现路线：LLM 统一模型调用服务

> 目标文档：[作业目标](./README.md)
> 验收文档：[验收清单](./验收清单.md)
> 参考实现：`course_code/week01/1-7/llm-gateway`（可对照结构，不直接提交）
> 整理日期：2026-11-06

## 1. 实施原则

1. **先跑通双协议最小闭环，再补能力**：不要一上来同时做流式、结构化、模板、观测、重试和限流。
2. **每个阶段都有可运行产物**：每完成一个 Phase，都能用 `curl` 或测试看到结果。
3. **统一接口优先**：调用方只改 `model` 就能切换协议；供应商差异全部收在 Adapter 里。
4. **确定性验证靠 mock，真实 API 只做冒烟**：重试、限流、结构化纠错这类场景不能依赖真实上游。
5. **P0 必做，P1 选做**：一天内完成时，优先保证验收六大功能，fallback/熔断/成本等放到后面。

## 2. 技术栈

| 层 | 选型 | 用途 |
| --- | --- | --- |
| Web 框架 | FastAPI + Uvicorn | HTTP 接口、SSE 流式响应 |
| HTTP 客户端 | httpx | 调用上游、`MockTransport` 测试 |
| 数据模型 | Pydantic v2 | 请求/响应/配置校验 |
| 存储 | SQLite + aiosqlite | Prompt 版本、调用记录、Checkpoint |
| 模板 | Jinja2 Sandbox + StrictUndefined | Prompt 渲染、变量检查 |
| Schema 校验 | jsonschema | 结构化输出二次校验 |
| 配置 | PyYAML + 环境变量 | 多供应商、多模型配置 |
| 测试 | pytest + pytest-asyncio | 单元/集成测试 |
| 代码质量 | ruff | 格式与静态检查 |

依赖尽量少，不要引入 LangChain 等重框架；这个作业的重点是协议适配和网关边界。

### 3.1 统一接口

建议只暴露一个统一入口，降低联调成本：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/v1/chat/completions` | 统一模型调用（支持 `stream` / `response_format` / `gateway_prompt`） |
| `GET` | `/v1/models` | 返回网关公开的模型别名 |
| `POST` | `/v1/prompts` | 新建 Prompt 版本 |
| `GET` | `/v1/prompts` | 列出 Prompt |
| `GET` | `/v1/prompts/{id}` | 获取指定版本/激活版本 |
| `POST` | `/v1/prompts/{id}/render` | 预览模板渲染结果 |
| `GET` | `/admin/usage` | 查询最近调用记录 |
| `GET` | `/healthz` | 健康检查 |
| `GET` | `/readyz` | 就绪检查 |

统一请求字段建议：

```json
{
  "model": "pro",
  "messages": [{"role": "user", "content": "你好"}],
  "stream": false,
  "temperature": 0.2,
  "top_p": 1,
  "max_tokens": 800,
  "response_format": null,
  "gateway_prompt": {
    "id": "reviewer",
    "version": 1,
    "variables": {"language": "Python"}
  }
}
```

### 3.2 Adapter 接口

```python
class ProviderAdapter(Protocol):
    protocol: str

    def build_request(self, req: UnifiedRequest) -> AdapterRequest:
        """统一请求 → 供应商路径 / headers / body"""

    def parse_response(self, data: dict) -> UnifiedResponse:
        """供应商非流式响应 → 统一响应"""

    def parse_stream_event(self, event: dict) -> UnifiedChunk | None:
        """供应商 SSE 事件 → 统一增量；无内容返回 None"""

    def extract_usage(self, data: dict) -> Usage:
        """从响应或流式事件中提取 Token 用量"""

    def map_error(self, status: int, body: dict) -> GatewayError:
        """供应商错误 → 统一错误码"""
```

关键点：

- Adapter 只负责协议转换，不负责重试、限流、记账。
- 所有供应商差异（认证头、字段名、事件名、错误结构）都收在 Adapter 内。
- 路由只认模型别名和协议，不认具体供应商 SDK。

### 3.3 配置示例

```yaml
service_name: unified-llm-gateway
database_url: data/gateway.db

retry:
  max_attempts: 3
  base_delay_seconds: 0.5
  max_delay_seconds: 8
  retry_statuses: [408, 429, 500, 502, 503, 504]

rate_limit:
  enabled: true
  # 每个模型独立一个桶
  requests_per_minute: 30
  burst: 5

providers:
  responses_provider:
    protocol: openai_responses
    base_url: ${RESPONSES_BASE_URL}
    api_key: ${RESPONSES_API_KEY}
    timeout_seconds: 120

  anthropic_provider:
    protocol: anthropic_messages
    base_url: ${ANTHROPIC_BASE_URL}
    api_key: ${ANTHROPIC_API_KEY}
    anthropic_version: "2023-06-01"
    timeout_seconds: 120

models:
  pro:
    provider: responses_provider
    upstream_model: deepseek-v4-pro

  flash:
    provider: anthropic_provider
    upstream_model: deepseek-v4-flash
```

注意：

- Base URL、模型 ID、版本头以实际供应商文档为准；不要把真实 Key 写进 YAML。
- 如果同一个供应商同时提供两种协议，就配置成两个 provider 条目。
- 限流的 key 应该是 `model`（或 `model + api_key`），保证“按模型独立限流”。

## 5. 分阶段实施

### Phase 0：脚手架与配置（约 0.5 天）

**目标**：服务能启动，配置能加载，健康检查可用。

- 初始化 `pyproject.toml`、`app/`、`tests/`
- 实现 `config.py`：YAML 读取、`${ENV_VAR}` 展开、缺省值
- 实现 `.env.example`、`gateway.example.yaml`
- 实现 `GET /healthz`、`GET /readyz`、`GET /v1/models`
- 配置日志与 `X-Request-ID`

**完成标志**：

```bash
uv run uvicorn app.main:app --reload --port 8000
curl -s localhost:8000/healthz
curl -s localhost:8000/v1/models -H "Authorization: Bearer $GATEWAY_API_KEY"
```

### Phase 1：统一 Schema + 双 Adapter + 非流式（约 1 天）

**目标**：同一套请求只改 `model`，分别走 OpenAI Responses 和 Anthropic Messages。

- 定义 `UnifiedRequest`、`UnifiedResponse`、`UnifiedChunk`、`Usage`
- 实现 `ProviderAdapter` 接口
- 实现 `OpenAIResponsesAdapter`
- 实现 `AnthropicMessagesAdapter`
- 实现 `ModelRouter`：`model` → provider → adapter
- 实现 `GatewayService.call_json()`
- 实现非流式错误映射

**协议映射重点**：

| 维度 | OpenAI Responses API | Anthropic Messages API |
| --- | --- | --- |
| 路径 | `/v1/responses` | `/v1/messages` |
| 认证 | `Authorization: Bearer <key>` | `x-api-key: <key>` + `anthropic-version` |
| 系统提示 | 顶层 `instructions` | 顶层 `system` |
| 对话输入 | `input`（字符串或消息数组） | `messages`（user/assistant） |
| 最大输出 | `max_output_tokens` | `max_tokens`（通常必填） |
| 结构化输出 | `text.format` | 原生能力因供应商而异；无原生能力时用 Schema 提示 + 本地校验 |
| 结束标记 | `response.completed` | `message_stop` |
| 用量 | `usage.input_tokens` / `output_tokens` | `usage.input_tokens` / `output_tokens` |

**完成标志**：

```bash
curl -s localhost:8000/v1/chat/completions \
  -H "Authorization: Bearer $GATEWAY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"pro","messages":[{"role":"user","content":"用一句话解释 LLM Gateway"}]}'

curl -s localhost:8000/v1/chat/completions \
  -H "Authorization: Bearer $GATEWAY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"flash","messages":[{"role":"user","content":"用一句话解释 LLM Gateway"}]}'
```

两个请求都返回统一结构，并在响应或日志中能看到实际 provider / protocol。

### Phase 2：SSE 流式（约 1 天）

**目标**：`stream=true` 时逐块返回，支持中断和 TTFT。

- 统一 SSE 输出格式：`data: {...}\n\n` + `data: [DONE]\n\n`
- 两个 Adapter 分别解析各自的流式事件
- `GatewayService.stream()`：逐块转发、记录 TTFT、处理客户端断开
- 客户端断开时关闭上游连接
- 流中途错误转成 SSE 错误事件，并以 `[DONE]` 结束
- 首个 chunk 发出后禁止跨模型重试/续写

**事件映射重点**：

| 统一语义 | OpenAI Responses | Anthropic Messages |
| --- | --- | --- |
| 文本增量 | `response.output_text.delta` | `content_block_delta` 中的 `text_delta` |
| 完成 | `response.completed` | `message_stop` |
| 用量 | `response.completed` 中的 `usage` | `message_delta` 中的 `usage` |
| 错误 | `error` / `response.failed` | `error` |

**完成标志**：

```bash
curl -N localhost:8000/v1/chat/completions \
  -H "Authorization: Bearer $GATEWAY_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"pro","stream":true,"messages":[{"role":"user","content":"写三行诗"}]}'
```

能看到多条 `data:`，最后是 `[DONE]`；`/admin/usage` 中 `stream=true` 且 `first_token_ms` 有值。

### Phase 3：结构化输出（约 0.5 天）

**目标**：`response_format` 约束模型返回合法 JSON，并能修复。

- 解析 `response_format.json_schema`（或简化版 `json_object`）
- 将 Schema 转成上游需要的格式
- 非流式：本地 `jsonschema.validate` 二次校验
- 校验失败：把具体错误反馈给模型，最多修复 1～2 次
- 修复仍失败：返回 422 + 统一错误码
- 流式：透传结构化输出；已发送内容后不做无损修复

**完成标志**：

- 正常请求返回合法 JSON
- mock 第一次返回非法 JSON、第二次合法，验证修复链路
- 连续非法时返回 422
- 流式结构化输出能被客户端逐块解析

### Phase 4：Prompt 模板与版本（约 0.5 天）

**目标**：模板可存储、可渲染、可版本引用。

- SQLite `prompts` 表：`id`、`version`、`content`、`role`、`is_active`、`created_at`
- `POST /v1/prompts` 创建新版本；`activate=true` 设为当前版本
- `POST /v1/prompts/{id}/render` 预览渲染
- 请求中的 `gateway_prompt` 引用模板：
  - `id`
  - `version`（可选，缺省用激活版本）
  - `variables`
- Jinja2 `SandboxedEnvironment` + `StrictUndefined`
- 调用方不能上传模板正文，只能引用已注册模板
- 变量作为数据渲染，不允许变量内容再次作为模板执行

**完成标志**：

- 同一模板 v1/v2 输出不同
- 变量替换正确
- 未知变量返回 422
- 注入样本不会突破模板边界

### Phase 5：可观测性（约 0.5 天）

**目标**：每次调用都有可查询的记录。

- SQLite `usage_events` 表
- 记录字段：
  - `request_id`、`model`、`provider`、`protocol`
  - `stream`、`status`、`status_code`
  - `input_tokens`、`output_tokens`、`total_tokens`
  - `reasoning_tokens`、`cached_tokens`（供应商支持时）
  - `latency_ms`、`first_token_ms`
  - `retries`、`fallbacks`、`error_type`、`error_code`
  - `prompt_id`、`prompt_version`
- 在 `finally` 中写记录，保证失败也有记录
- `GET /admin/usage?limit=20` 查询
- 响应头返回 `X-Request-ID`

**完成标志**：

- 非流式、流式、失败调用各有一条记录
- 流式记录有 TTFT
- 失败记录有错误码和重试次数

### Phase 6：韧性基础（约 0.5 天）

**目标**：上游异常时网关能兜住，并返回统一错误。

- 定义 `GatewayError` 及子类：`UpstreamError`、`StructuredOutputError`、`RateLimitError`
- 统一错误响应：

```json
{
  "error": {
    "message": "Rate limit exceeded",
    "type": "rate_limit_error",
    "code": "rate_limit_exceeded",
    "param": null
  }
}
```

- 指数退避重试：`base_delay * 2^attempt` + jitter，最多 3 次
- 只重试网络错误、超时、429、5xx；普通 4xx 不重试
- 流式已开始后不重试
- 按模型独立的 token bucket；超限返回 429 + `Retry-After`
- 可选：fallback、熔断器

**完成标志**：

- mock 500/超时能看到重试次数和退避
- 400 不重试
- 突发请求返回 429，模型 A 限流不影响模型 B

### Phase 7：验证与交付（约 0.5～1 天）

- `pytest` 覆盖 Adapter、流式、结构化、模板、观测、重试、限流
- `scripts/verify.py` 端到端跑一遍六大功能，打印通过/失败
- README：启动、环境变量、两个模型的 curl、六大功能示例、错误码、测试方式
- `evidence/` 保存命令输出、日志、截图
- 检查无 API Key、无 `.env`

**完成标志**：

```bash
uv run pytest -q
uv run python scripts/verify.py
uv run ruff check .
```

全部通过，README 可按步骤复现。

## 8. 测试策略

### 8.1 确定性测试

用 `httpx.MockTransport` 模拟上游，覆盖：

- 两个 Adapter 的非流式请求/响应映射
- 两个 Adapter 的 SSE 事件解析
- 429/500/超时 → 重试次数与退避
- 400 → 不重试
- 按模型限流 → 429
- 结构化输出非法 → 修复 → 成功
- 结构化输出连续非法 → 422
- Prompt 版本/变量/注入
- usage 字段完整性

### 8.2 真实冒烟

`scripts/smoke_real.py` 读取真实环境变量，分别调用两个模型：

- 非流式一次
- 流式一次
- 结构化一次
- 打印 provider、模型、TTFT、usage

没有真实 Key 时自动跳过，不阻塞 CI。

### 8.3 验证脚本

`scripts/verify.py` 对运行中的网关执行：

1. 健康检查
2. 模型列表
3. 两个模型的非流式调用
4. 两个模型的流式调用
5. 结构化输出
6. Prompt 创建/渲染/引用
7. 查询 usage
8. 触发限流并检查 429
9. 输出通过/失败汇总

重试和上游错误更适合放在 pytest 里，用 mock 保证可重复。

## 9. 常见坑

1. **把两种协议做成两个模型名**：必须真的走不同端点、不同认证、不同报文结构。
2. **SSE 分帧**：事件之间必须有空行；要处理 `\r\n`、多行 `data:`、跨 chunk 的半个 JSON。
3. **`max_tokens` 差异**：Anthropic Messages 通常要求 `max_tokens`；OpenAI Responses 用 `max_output_tokens`。
4. **系统提示位置**：Responses 用 `instructions`，Messages 用顶层 `system`。
5. **用量字段差异**：input/output/reasoning/cached 的字段名和口径不同，README 要写清。
6. **流式重试**：首个 chunk 发出后不能重试或切换模型，否则重复输出。
7. **限流粒度**：按模型建桶，不要全局一个桶。
8. **结构化输出**：Anthropic 侧不一定有与 OpenAI 完全相同的 `response_format`，要在 Adapter 里做能力映射。
9. **Prompt 注入**：模板沙箱只能防模板语法注入，不能防模型级 Prompt Injection；不可信输入仍要隔离。
10. **密钥**：只放环境变量/Secrets，不提交 `.env`、不写进 README。
