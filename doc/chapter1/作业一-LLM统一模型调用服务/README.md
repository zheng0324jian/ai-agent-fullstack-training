## 0. 一句话目标

用一套统一 API，屏蔽 **OpenAI Responses API** 与 **Anthropic Messages API** 的协议差异，让调用方只改 `model` 字段，就能获得流式输出、结构化输出、Prompt 版本管理、可观测性、重试和按模型限流，并用验证脚本证明这些能力。

## 1. 作业定位

这不是一个聊天产品，也不是 Agent，而是 **LLM Gateway（模型访问层）**：

- 对上：提供统一、稳定的模型调用接口
- 对下：适配多个供应商、多种 API 协议
- 在网关层集中处理：鉴权、路由、流式、结构化输出、Prompt 模板、Token/延迟观测、重试、限流

它对应第一章从「API 调用 → 参数与 Token → 错误处理 → 流式 → Prompt → 结构化输出 → Gateway → 统一服务」的完整链路，是第一章的综合验收。

## 2. 官方要求

### 2.1 建议选型

为达到“两种不同 API 协议”的训练目标，作业建议：

| 模型 | 协议 |
| --- | --- |
| DeepSeek v4 pro | OpenAI Responses API |
| DeepSeek V4 flash | Anthropic Messages API |

也可以自行选择其他组合，但必须确保两种协议存在实质差异，而不是同一个 SDK 换两个模型名。

### 2.2 核心要求

1. **统一抽象层**：设计统一调用接口，通过适配器模式封装不同 API 协议；根据请求中的 `model` 字段动态路由到对应适配器，屏蔽底层鉴权、请求体结构和返回格式的差异。
2. **三大能力**：
   - **流式输出**：支持 `stream=true`，以 SSE 格式逐块返回
   - **结构化输出**：支持 `response_format` 约束返回合法 JSON
   - **提示词版本管理**：支持模板存储、变量替换和版本引用
3. **可观测性**：记录每次调用的 Token 消耗（含分类统计）和延迟（含首 Token 延迟）。
4. **韧性基础**：统一错误码封装 + 指数退避重试（最多 3 次）+ 按模型独立限流（超限返回 429）。

### 2.3 交付物

- 完整源码 + README（含启动指南和 `curl` 示例）
- 验证脚本，覆盖全部功能点

### 2.4 验收标准

> 两个模型调用均可正常工作；流式、结构化输出、模板引用、可观测数据、重试和限流六大功能均有可验证的证据。

注意关键词是**可验证的证据**：不能只在 README 里写“已实现”，要有命令、输出、日志或测试结果。

## 3. 目标拆解

### G1. 统一抽象层（P0）

**目标**：调用方只面对一套接口，不感知供应商 SDK、鉴权方式和报文结构。

需要做到：

- 定义统一的请求/响应模型，例如 `model`、`messages`、`stream`、`response_format`、`prompt` 等
- 为两种协议分别实现 Adapter：
  - OpenAI Responses Adapter
  - Anthropic Messages Adapter
- 通过 `model` 或模型别名路由到对应 Adapter
- 屏蔽差异：认证头、请求体字段、响应结构、流式事件格式、错误结构
- 配置化：模型别名、供应商、Base URL、API Key、超时、限流参数不写死在代码里
- 调用方不需要持有任何上游供应商密钥

**验收证据**：同一段客户端代码，只改 `model` 就能分别调用两个协议；响应中能看出实际使用的 provider/model。

### G2. 流式输出（P0）

**目标**：`stream=true` 时以 SSE 逐块返回，而不是等完整结果再一次性返回。

需要做到：

- 统一输出 `data: {...}\n\n` 格式，并以 `data: [DONE]` 结束
- 首 Token 延迟（TTFT）可观测
- 客户端断开时取消上游请求，避免继续消耗 Token
- 上游流式错误转成统一的 SSE 错误事件
- 首个数据块发出后不跨模型续写，避免重复或语义错乱
- 可选：长文本断线后的 Checkpoint / 状态保存（对应课程 2-3）

**验收证据**：`curl -N` 能看到增量输出；记录中包含 TTFT；中断客户端后上游请求被取消；模拟上游错误能看到统一错误事件。

### G3. 结构化输出（P0）

**目标**：通过 `response_format` 约束模型返回合法 JSON，并在不合规时具备纠错能力。

需要做到：

- 支持 JSON Schema / Pydantic 模型约束
- 将统一的 `response_format` 语义映射到不同协议：
  - 有原生结构化输出能力的供应商直接透传
  - 没有原生能力的供应商用 Schema 提示 + 本地校验 + 修复重试
- 对返回结果做本地二次校验
- 校验失败时把错误反馈给模型修复；修复仍失败则返回统一错误
- 流式结构化输出要能处理跨 chunk 的半个 JSON

**验收证据**：正常请求返回符合 Schema 的 JSON；构造非法输出时能触发修复/重试；最终失败返回统一错误码。

### G4. Prompt 版本管理（P0）

**目标**：Prompt 不是散落在代码里的字符串，而是可存储、可渲染、可版本化的资产。

需要做到：

- 模板存储：模板 ID、正文、版本号、激活状态
- 变量替换：调用方传变量，网关负责渲染
- 版本引用：请求指定模板 ID + 版本；不同版本可复现不同行为
- 调用方不能上传模板正文，只能引用已注册模板（降低注入和越权风险）
- 处理模板注入风险：变量转义、模板沙箱、长度限制
- 可选：模板变更审计与回滚

**验收证据**：同一模板不同版本输出不同；变量替换生效；未知变量/未知版本返回 4xx；注入样本不会突破模板边界。

### G5. 可观测性（P0）

**目标**：每次模型调用都能回答“用了多少 Token、花了多久、是否重试、是否失败”。

建议记录字段：

- `request_id`、`model`、`provider`、`protocol`
- 状态：`success` / `error` / `cancelled`
- 延迟：总延迟、TTFT
- Token：输入、输出、总计；如供应商支持，再记录 reasoning / cached tokens
- 重试次数、fallback 次数、错误码
- 可选：成本估算

落地方式可以是 SQLite、JSONL 或结构化日志；关键是有查询/查看方式。

**验收证据**：一次非流式调用和一次流式调用都能查到完整记录；流式记录包含 TTFT；失败调用有错误码和重试次数。

### G6. 韧性基础（P0）

**目标**：上游不稳定时，网关要能兜住，而不是把原始异常直接抛给调用方。

需要做到：

- 统一错误码，例如：`INVALID_REQUEST`、`AUTH_ERROR`、`RATE_LIMITED`、`TIMEOUT`、`UPSTREAM_ERROR`、`CONTENT_FILTERED`、`STREAM_ABORTED`
- 指数退避重试，最多 3 次；只对可安全重试的错误重试
- 流式请求一旦已经开始返回内容，不再重试或切换模型
- 按模型独立限流，超限返回 429 和统一错误体
- 可选：fallback 到备用模型、熔断器（课程 1-3 / 5-1 有涉及）

**验收证据**：模拟 500/超时能看到重试次数和退避间隔；超过限制返回 429；模型 A 的限流不影响模型 B；流式开始后失败不会重复请求。

### G7. 交付物与验证（P0）

必须包含：

- 可运行源码
- README：环境变量、启动方式、两个模型的 `curl` 示例、六大功能的调用示例
- 验证脚本：覆盖双模型、流式、结构化、模板、观测、重试、限流
- 测试策略：可重复的 mock/fake 上游 + 真实 API 冒烟测试
- 不在仓库中提交 API Key

**验收证据**：从干净环境按 README 能启动；运行验证脚本能一次跑完所有功能点；README 中有结果截图或输出片段。

| 能力 | 最小证据 | 建议覆盖 |
| --- | --- | --- |
| 双协议 / 双模型 | 两个 `model` 都能调用成功 | 分别打印 provider、协议、响应摘要 |

| Prompt 模板 | 不同版本/变量渲染结果不同 | 版本切换、未知变量、注入样本 |
| 可观测性 | 每次调用一条完整记录 | 非流式、流式、失败、重试 |
| 重试 | 失败后按指数退避重试，最多 3 次 | 500、超时、不可重试错误 |
| 限流 | 超限返回 429，错误体统一 | 单模型突发、跨模型隔离 |

## 6. 范围边界

**必须做（P0）**

- 两种不同协议的真实适配
- 流式、结构化、模板版本、可观测、重试、限流
- README + 验证脚本 + 可复现证据

**建议做（P1）**

- fallback / 熔断
- 成本估算
- 请求 ID 贯穿日志
- 流式 Checkpoint
- Docker 化

**暂不做（P2）**

- Agent Loop、工具调用、RAG（后续章节）
- 前端聊天界面
- 多租户计费、复杂配额
- 生产级高可用、跨区域部署

## 7. 关键风险与待确认

1. **协议差异不是模型差异**：两个模型必须走不同协议；不要用同一个 OpenAI SDK 换两个模型名冒充。
2. **Anthropic Messages API 与 OpenAI 的结构化输出能力不同**：需要适配器层做语义映射，不能假设都有原生 `response_format`。
3. **Token 分类口径不同**：reasoning、cached tokens 是否返回、是否计入总量，各供应商可能不同；README 要写清统计口径。
4. **“最多 3 次”要明确语义**：是总尝试 3 次，还是首次之外再重试 3 次；建议在 README 和测试中固定一种解释。
5. **流式重试边界**：首个 chunk 发出后不要重试或切换模型，否则会出现重复内容。
6. **限流粒度**：作业要求“按模型独立限流”，不要做成全局一个桶。
7. **密钥安全**：上游 API Key 只存在网关环境变量/配置中，不进入客户端、不提交仓库。

## 8. 建议推进顺序

1. 配置与模型注册表（model alias → protocol / provider / base_url / key）
2. 统一请求/响应模型 + 统一错误模型
3. 两个 Adapter（先跑通非流式）
4. SSE 流式 + 中断 + TTFT
5. 结构化输出 + 校验/修复
6. Prompt 模板 + 版本
7. 调用记录（Token / 延迟 / 状态）
8. 重试 + 按模型限流
9. 验证脚本 + README + 证据整理
