## MCP 服务接入与发现

### Q1：MCP 服务只能配置到 Agent 本地才能被发现吗？外网 MCP 是否应该有一个统一的服务发现中心？

- 关联课程：第二章 MCP（服务接入与服务发现）
- 记录日期：2026-11-13

**一句话回答**：不是只能配在本地，但**目前主流 MCP 客户端仍然要求显式添加一次服务器**（本地 stdio 命令或远程 URL）。MCP 是 Client ↔ Server 协议，不是服务发现协议；“统一发现中心”正在形成，但形态是**注册表 + 域名级 Server Card + 网关聚合**，而不是所有 Agent 无条件自动接入的单一中心。

**先区分两件事**：

| 层次 | 解决的问题 | 典型机制 |
| --- | --- | --- |
| 发现（Discovery） | Agent 怎么知道“有这个服务、地址是什么、支持哪些协议版本” | MCP Registry、Server Card、AI Catalog、`server/discover` |
| 接入（Connection） | Agent 怎么连上、怎么鉴权、能调用哪些工具 | stdio / Streamable HTTP、OAuth、`initialize` + `tools/list` |

关键点：**发现可以自动化，接入仍然需要信任与授权决策**。

**为什么“本地配置”仍是常态**：

1. MCP 规范只定义 Client 与 Server 之间的通信，没有规定全局目录服务。
2. MCP 暴露的是**可执行工具**，不是只读数据。自动连接陌生服务器会带来权限、数据、计费、Prompt Injection 等风险。
3. 客户端需要知道传输方式（stdio 还是 Streamable HTTP）、鉴权方式（OAuth / API Key）、允许使用的工具范围，这些目前都要显式配置。
4. 企业环境还需要 allowlist、审计、配额和版本锁定，天然要求“先审批、再接入”。

**目前存在的三层发现机制**：

**1）注册表 / 目录（Registry & Catalog）**

- 官方 MCP Registry（`registry.modelcontextprotocol.io`），以及 Smithery、mcp.so、Glama、PulseMCP、Docker MCP Catalog 等第三方目录。
- 注册表用 `server.json` 描述服务：名称、描述、版本、安装方式（本地包或远程 URL）。
- 客户端可以搜索、一键安装，但**最终仍会把条目写入自己的配置**，不是运行时自动挂载。
- 类比：应用商店能帮你找到 App，但安装和授权仍由本机完成。

**2）域名级发现（Server Card / AI Catalog）**

- SEP-2127 **MCP Server Cards** 是 2026 年 10 月定稿的扩展提案（可选扩展，不是核心规范的强制要求）。
- 服务方在 `https://<mcp-endpoint>/server-card` 提供静态卡片：名称、版本、连接地址、支持的协议版本。
- 域名级入口是 `https://<domain>/.well-known/ai-catalog.json`，列出该域下所有 MCP 服务的卡片地址。
- 客户端拿到域名后，可以自动读取卡片并完成预配置。
- 卡片**故意不包含工具列表**：工具会随用户身份、权限和部署状态变化，静态文档容易过期；实际工具仍要通过 `tools/list` 获取。
- 卡片是**自报信息**，只用于发现，不是可信背书；是否接入仍要做来源、权限和数据处理审查。

**3）连接后的运行时发现**

- 经典流程：`initialize` 握手 → `tools/list` / `resources/list` / `prompts/list`。
- MCP 2026-07-28 规范新增 `server/discover`：已知端点后，一次调用返回服务端支持的版本、能力和身份信息。
- 它解决的是“连上之后确认对方是谁、能做什么”，不能替代连接前的地址发现。

**工程上最接近“统一服务中心”的形态：MCP Gateway**

- 常见实现：Docker MCP Gateway、MetaMCP、IBM ContextForge 等。
- Agent 只配置一个 MCP 端点；网关后面挂 N 个上游 MCP 服务，统一做路由、鉴权、审计、限流和工具白名单。
- 对 Agent 来说，网关就是“一个发现中心”；对平台来说，它是统一治理入口。
- 这是架构模式，不是 MCP 协议规定；网关本身仍是一个普通的 MCP Server。

**落到 OpenCode**：

```sh
# 远程 MCP：默认走 OAuth
opencode mcp add context7 --url https://mcp.context7.com/mcp

# 本地 MCP：stdio 启动子进程
opencode mcp add everything -- npx -y @modelcontextprotocol/server-everything
```

- 远程服务用 Streamable HTTP，本地服务用 stdio。
- 配置写入 `opencode.jsonc` 的 `mcp.servers`，客户端启动时连接；目前没有“自动扫描注册表”的能力。
- 以 browse 为例：安装脚本把它写入 `~/.config/opencode/opencode.jsonc` 后，Agent 才能看到它的工具，这也印证了“接入需要显式配置”。

**常见误区**：

- “有注册表 = Agent 自动能用”：注册表只提供元数据和安装入口，不负责运行时连接。
- “远程 MCP 不需要配置”：仍然需要 URL、鉴权和权限范围。
- “Server Card 是安全认证”：卡片是自报的，能力与身份要在握手和运行时校验。
- “工具列表可以静态发现”：工具取决于用户、权限和部署，必须通过 `tools/list` 获取。

**结论**：

- 短期：显式配置仍是主流，尤其是涉及写操作、付费和企业数据的服务。
- 中期：注册表 + `/.well-known` 发现 + Server Card 会降低配置成本，但不会消灭授权环节。
- 长期：更可能是“多个注册表 + 域名自发现 + 企业网关”的组合，而不是一个所有 Agent 无条件接入的单一中心。原因不是技术做不到，而是**信任、权限、计费和责任边界**必须由人或客户端做决定。
